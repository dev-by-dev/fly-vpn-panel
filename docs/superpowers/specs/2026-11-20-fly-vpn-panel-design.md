# fly-vpn-panel — дизайн-док (v1)

Дата: 2026-11-20. Статус: одобрен пользователем 2026-11-20.
Процесс: SDD. Ветки: `<фича>-20261120-NN` от `dev`. Репо: **публичный** GitHub, все артефакты обезличены (§3).
Архитектурные решения: `docs/adr/` (ADR-0001…0008, accepted).

## 1. Intent и why

Своя web-панель для VPN-сервера. Боли текущей Remnawave (подтверждены пользователем):

1. **Неинформативна**: после создания профиля непонятно, какие устройства подключены и сколько трафика потребляют.
2. **Санитайзер шаблонов** вырезает routing-правила, генератор подписок кривой (CLASH всегда пустой, xPadding-поля не эмитятся).
3. **Лишняя сложность**: panel + node + postgres + valkey — четыре сущности вместо одной.
4. Хочется **полный контроль над xray-конфигом без прослойки**, как в 3x-ui.

Новая панель — **будущая замена Remnawave** (не параллельный игрушечный инструмент). Remnawave пока работает как есть на старом сервере; новая панель разворачивается на **выделенной VPS** (ADR-0008) — существующий стек физически не затрагивается.

Главная фича v1 — видимость: кто подключён (устройства) + сколько трафика (по юзерам).

## 2. Goals / Non-goals / Anti-goals

**Goals v1 (подтверждён пользователем «v1 да»):**
- Auth: один админ, пароль + JWT + опциональный TOTP/2FA.
- Жизненный цикл xray: старт/стоп/рестарт, валидация конфига ДО применения.
- Inbound CRUD: VLESS + XHTTP + Reality.
- Юзеры CRUD + expiry + квота трафика (период сброса + авто-отключение/включение) + лимит устройств по distinct онлайн-IP.
- Трафик по юзерам + онлайн-устройства (гибрид, см. §6.7).
- Подписки: 4 формата (base64 / json / mihomo / clash).
- Routing через JSON-редактор полного конфига (без санитайзера).
- Дашборд: трафик день/неделя/месяц, онлайн, состояние xray.
- Деплой на выделенной VPS за поддоменом `<PANEL_DOMAIN>` собственного Caddy.

**Non-goals v1 (пользователь подтвердил «потом»):** singbox/stash форматы · визуальный конструктор правил + библиотека пресетов + док «как создавать правила» · мультинода · per-inbound membership (squads) · миграция юзеров из Remnawave · Telegram-уведомления · API-токены для скриптов.

**Anti-goals (провал даже если технически работает):**
- Затронуть действующий стек на старом сервере при деплое (выделенная VPS исключает это by construction; любые действия на старом сервере — только отдельное явное «да»).
- Санитайзер/скрытая порча пользовательских правил и конфигов.
- Непрозрачная генерация: юзер должен видеть итоговый xray-конфиг и итоговую подписку.
- Возврат к контейнерной зоопарк-сложности: деплой = один бинарник + xray.
- Утечка реальных адресов/имён/путей в публичный репо (§3).

## 3. Constraints

**Публичный репо — обезличивание (директива пользователя 20.11.2026):**
- Никаких реальных IP, доменов, имён серверов/провайдеров/пользователей, путей к секретам, деталей клиентской сети в любом артефакте репо (доки, код, комментарии, фикстуры, тесты).
- Плейсхолдеры: `<ENTRY_IP>` (публичный IP VPS, вход=выход), `<PANEL_DOMAIN>` (домен UI + подписок), `<EGRESS_IP>` (опциональный отдельный egress-IP; пуст → `sendThrough` опускается; задел на будущее «вход≠выход»).
- Реальные значения живут ТОЛЬКО на сервере (`/opt/flypanel/.env`, chmod 600, gitignored) и в приватном runbook оператора (вне репо).
- История git должна быть чистой ДО первого push (черновой коммит спеки перезаписать).

**Выделенная VPS (ADR-0008, разведка 20.11.2026):**
- Ubuntu 24.04 LTS, 1 vCPU / 1 GB RAM / 10 GB disk, один публичный IP (вход=выход). Swap отсутствует → создать 2 GB swapfile при деплое. Docker не нужен: Caddy нативный, панель + xray под systemd.
- Доступ — только через SSH-инструментарий оператора, **явное разрешение на каждое действие**; SSH-порт не менять. Агент провайдера (8080 / 127.0.0.1:8189) НЕ ТРОГАТЬ.
- Старый сервер с действующим стеком Remnawave — физически отдельная машина; деплой её не затрагивает by construction. Единственное разрешённое касание — read-only чтение продакшн-шаблонов (§6.6).
- Порты 80/443/8443/3002/10811 свободны (проверено разведкой). Панель bind **127.0.0.1:3002**, xray API **127.0.0.1:10811**, VPN-вход `<ENTRY_IP>:8443`.
- Freedom outbound без `sendThrough` (один IP). `<EGRESS_IP>` пуст → генератор опускает поле; второй IP можно добавить позже без правок кода.
- DNS: A-запись `<PANEL_DOMAIN>` сейчас указывает на старый сервер — оператор перенаправит на `<ENTRY_IP>` при деплое. LE-сертификат Caddy получит сам (HTTP-01, порт 80).
- Клиенты: современные ядра mihomo ≥1.19.22 (FlClash, Clash Verge) и v2rayNG — VLESS+XHTTP+Reality поддерживают. Classic Clash (ядро <1.19.22) не поддерживаем.
- Секреты не печатать; результаты работ фиксировать в приватном журнале оператора (вне репо).

## 4. Approaches (что рассматривали и почему так)

| Решение | Выбрано | Альтернативы и почему нет |
|---|---|---|
| Топология | **A** (выбор пользователя, ADR-0001): Reality для VPN на своём порту 8443, xray сам терминирует TLS; UI за собственным Caddy на поддомене | B: всё за одним Caddy — связывает VPN с reload-рисками, h2c-прослойка, не «полный контроль». C: второй Caddy на 8443 + LE DNS-01 — лишняя сущность и возня с сертификатами, выигрыша нет |
| Размещение | **Выделенная VPS** (выбор пользователя 20.11.2026, ADR-0008): новый стек один на сервере, старый не затрагивается | Coexist на старом сервере — риск для прод-стека, тихие окна reload, общие порты, docker-gateway bind |
| Бэкенд + БД | **Go + SQLite, один бинарник** (Go — требование пользователя; SQLite подтверждён, ADR-0002): WAL + `_busy_timeout`, бэкап = копия файла | Postgres — +контейнер/бэкапы/RAM/обслуживание, выигрыш 0 до тысяч юзеров/мультиноды. Node/Rust/Python — тяжелее/дольше/нет нативного gRPC-преимущества. Прецедент: 3x-ui = Go+SQLite+xray |
| Владение xray | **Дочерний процесс панели** (3x-ui style, ADR-0003): панель владеет жизненным циклом целиком | Отдельный systemd-unit — два владельца, рассинхрон; node-агент — прослойка, от которой уходим |
| Фронтенд | **Svelte 5 + Vite + Tailwind v4 + shadcn-svelte**, SPA вшивается в Go-бинарник через `embed.FS` (мой выбор, делегирован; ADR-0004): деплой = один файл, лёгкий бандл | React/Next — тяжелее, SSR не нужен; серверные шаблоны — не «красиво/современно» |
| Видимость | **Гибрид через xray stats API** (мой выбор, ADR-0005): трафик по юзерам (QueryStats) + онлайн-устройства IP/last-seen (**GetStatsOnlineIpList / GetAllOnlineUsers** — xray сам отдаёт онлайн-IP по юзеру; парсинг access log НЕ нужен) | Per-device трафик — xray stats только по uuid, надёжно не сделать; access-log парсинг — сложнее и не нужен при наличии API. NAT-оговорка: один IP на весь роутер, «устройство» = distinct source IP |
| Квота | **Период сброса + авто-возврат** (выбор пользователя, ADR-0006): up+down, период на юзера (без сброса/день/неделя/месяц) | Пожизненная + ручной сброс — проще, но не совпадает с привычкой Remnawave |

## 5. Архитектура и топология

```
клиент → vless://<ENTRY_IP>:8443 (Reality, sni=dest-сайт, XHTTP stream-up)
       → xray (дочерний процесс flypanel) → freedom (sendThrough <EGRESS_IP> если задан) → internet

браузер → https://<PANEL_DOMAIN> → Caddy :443 (собственный, нативный)
       → reverse_proxy 127.0.0.1:3002 → flypanel (Go, SPA embed)
       → SQLite /opt/flypanel/data/panel.db
       → gRPC 127.0.0.1:10811 (dokodemo-door API inbound в xray)
       → подписки: https://<PANEL_DOMAIN>/sub/<token>[/base64|/json|/mihomo|/clash]
```

- **flypanel**: один Go-бинарник, systemd unit `flypanel.service`, слушает **127.0.0.1:3002** (loopback: нативный Caddy достучится, наружу не торчит). SPA вшита (`embed.FS`).
- **xray**: бинарник официального релиза **v26.11.9** (пин при деплое) в `/opt/flypanel/bin/xray`, запускается панелью как дочерний процесс. Конфиг `/opt/flypanel/data/xray.json` — генерируется панелью из БД (БД = source of truth).
- **xray API inbound**: dokodemo-door `127.0.0.1:10811` (панель на хосте → loopback работает), tag `api`. StatsService + HandlerService + routing service.
- Layout `/opt/flypanel/`: `flypanel`, `bin/xray`, `data/panel.db`, `data/xray.json`, `logs/`, `.env` (реальные значения, chmod 600, gitignored).
- UFW при деплое: allow 22/80/443/8443/tcp (мир). 3002/10811 — только loopback, правил наружу не нужно. Swap 2 GB создать.
- Caddy: **нативная установка** (официальный репозиторий), Caddyfile с нуля: блок `<PANEL_DOMAIN> { reverse_proxy 127.0.0.1:3002 }`. Бэкап `cp -a Caddyfile Caddyfile.bak-YYYYMMDD` перед правками, `caddy validate` → `systemctl reload caddy`, явное «да» пользователя, верификация runtime :2019 + LE. Тихое окно не нужно (на этом Caddy только наш сайт); reload рвёт established-соединения панели — предупреждать.

## 6. Компоненты бэкенда

### 6.1 Auth
- Один админ. Создаётся **CLI на сервере** `flypanel admin init` (интерактивно: пароль). Публичной регистрации НЕТ (anti-goal: кто-то зарегистрируется раньше).
- Пароль: argon2id. JWT: access 15 мин + refresh 7 дней, httpOnly cookies, SameSite=Strict; refresh-токены в БД (отзыв при logout/password change).
- **2FA TOTP (RFC 6238, pquerna/otp v1.5.0)**: включение опциональное, после включения обязателен при логине. Enrollment: секрет + `otpauth://` URI → **QR рендерит фронт** (npm-либа, Go-зависимость для QR не нужна). 10 backup-кодов (хеши, одноразовые). Отключение — только с действующим TOTP/backup-кодом.
- Rate limit логина (напр. 5 попыток/мин с IP).

### 6.2 Юзеры
- Поля: username, uuid (VLESS id), sub_token (случайный короткий), expiry, quota_bytes (0 = безлимит), **quota_period (none|day|week|month)**, quota_reset_at, device_limit (0 = безлимит, **дефолт 0**), disabled, disabled_reason (quota|device_limit|expired|manual), created.
- **Квота (ADR-0006)**: считается **up+down суммарно**. Периодный счётчик = сумма дельт из traffic_samples с начала периода. Превышение → горячее удаление из inbound + disabled_reason=quota. Начало нового периода → счётчик обнуляется, юзер **авто-включается** (если был отключён по квоте). Админ может сбросить/поднять лимит вручную → авто-включение. Период none = пожизненный лимит (возврат только вручную).
- **device_limit**: жёсткий, по **concurrent** distinct онлайн-IP (GetStatsOnlineIpList). Превышение → горячее отключение (disabled_reason=device_limit); **авто-возврат** когда онлайн-IP снова ≤ лимита (следующий поллинг). NAT-оговорка в UI: один роутер = один IP; телефон+дом = два. Дефолт безлимит. Известное ограничение: concurrent-лимит не мешает ротации устройств по очереди — это осознанно (окно накопления — потом, если понадобится).
- **expiry**: истечение → горячее отключение (disabled_reason=expired), проверка и на поллинге, и при запросе подписки. Админ продлил → авто-включение на следующем поллинге.
- **Membership v1**: все активные юзеры состоят во **всех включённых inbound** (без join-таблицы). Per-inbound squads — non-goal v1. Подписка отдаёт ссылки по всем включённым inbound.
- Статистика xray keyed по email = username.

### 6.3 Inbound / протокол
- v1: VLESS + XHTTP + Reality. Структурированная форма основных параметров: port (дефолт 8443), path (дефолт `/xhttp`), mode (дефолт stream-up), Reality dest (дефолт **`www.microsoft.com:443`** — TLS1.3+H2; конфигурируемый), serverNames, privateKey/publicKey (генерация панелью), shortIds, fingerprint (дефолт chrome).
- **Raw JSON** для остальных параметров inbound (3x-ui style) — полный контроль, без санитайзера.
- Модель данных поддерживает N inbound; UI управляет списком.
- Итоговый xray-конфиг всегда виден в UI (вкладка «Конфиг»).

### 6.4 Жизненный цикл xray и применение конфига
- **Структурные изменения** (routing, параметры inbound, новый inbound): собрать JSON из БД → **валидация `xray run -test -c`** → только при успехе записать файл → рестарт дочернего процесса (~1–2 с даунтайм, UI предупреждает). При провале валидации — старый конфиг нетронут, ошибка в UI.
- **Юзеры/квоты/лимиты/expiry**: горячо через gRPC `HandlerService.AlterInbound` (AddUserOperation/RemoveUserOperation) — без рестарта, соединения живы.
- Крах xray → авто-рестарт с backoff, статус/алерт в UI. Старт/стоп/рестарт кнопками.
- Policy в конфиге: level 0 `statsUserUplink/statsUserDownlink/statsUserOnline = true` (иначе онлайн-IP не собираются), юзеры level 0. Outbounds: `freedom` (sendThrough `<EGRESS_IP>` **если задан**, иначе опущен), `block`. Routing v1: пустой rules по умолчанию (юзер добавляет сам через редактор).

### 6.5 Routing
- v1: **JSON-редактор** секции routing полного конфига в UI. Никакого санитайзера — что ввёл, то и применилось (после валидации).
- Пресеты/визуальный конструктор/док «как создавать правила» — потом (non-goal v1).

### 6.6 Подписки
- URL: `https://<PANEL_DOMAIN>/sub/<token>`; суффиксы `/base64` `/json` `/mihomo` `/clash`. Базовый URL: UA-fallback (v2rayNG → base64; FlClash / clash-verge lowercase → mihomo; прочее → base64).
- Форматы:
  - **base64**: список `vless://` ссылок (Reality+XHTTP параметры: type=xhttp, path, mode, security=reality, pbk, sid, sni, fp, encryption=none).
  - **json**: массив клиентских xray-конфигов (один inbound → один конфиг; routing из шаблона).
  - **mihomo**: yaml (proxies + proxy-groups + rules).
  - **clash**: yaml, mihomo-совместимый (все целевые Clash-клиенты на ядре ≥1.19.22; classic Clash не поддерживаем — non-goal).
- **Шаблоны per-format**: редактируемый raw-текст в UI с плейсхолдерами, хранится в БД, **без санитайзера**. Дефолтные шаблоны при установке **зеркалят текущие продакшн-шаблоны** действующей панели (RU-direct правила, adblock rule-provider anti-ad.net + 10 Google/YouTube доменов, sniffer, `ipv6: false`, Telegram IP-CIDR → proxy no-resolve) — чтобы замена не потеряла настройки. Источник: оператор **разрешил read-only чтение** текущих шаблонов (файлы/БД действующей панели) на этапе имплементации; конкретные пути — в приватном runbook, не в репо. Зеркало проверяется диффом. Это стартовый текст, юзер правит свободно.
- Публичный доступ: только `/sub/*` без JWT; токен = секрет юзера.

### 6.7 Видимость и статистика (главная фича)
- Поллер gRPC раз в 30 с (конфигурируемо):
  - `QueryStats` per-user uplink/downlink (паттерн `user>>><email>>>>traffic>>>uplink`, reset=false) → дельты в SQLite.
  - `GetAllOnlineUsers` + `GetStatsOnlineIpList` per-user → онлайн-IP + last-seen. **Семантику методов проверить при имплементации** (proto из main, релиз v26.11.9); fallback если API не даст IP — парсинг access log xray (только тогда).
- SQLite: `traffic_samples(user, ts, up_delta, down_delta)` → агрегаты день/неделя/месяц + периодный счётчик квоты; `devices(user, ip, first_seen, last_seen)`.
- Enforcement на поллинге: квота / device_limit / expiry (§6.2) → горячий RemoveUser + disabled_reason; авто-возврат по условиям §6.2.
- Счётчики xray сбрасываются при рестарте — дельты фиксируются часто (поллинг 30 с), потеря ≤ интервала.
- Дашборд: графики трафика по юзерам (день/неделя/месяц), список онлайн-устройств (юзер, IP, last-seen), состояние xray (running/version/uptime/restarts), суммарный трафик.

### 6.8 БД (SQLite, modernc.org/sqlite v1.62.0, pure Go)
- DSN: `_journal_mode=WAL&_busy_timeout=5000&synchronous=FULL`. Один писатель.
- Таблицы (эскиз): `admin`, `users`, `inbounds`, `settings` (key/value: шаблоны, Reality-ключи, интервал поллинга), `traffic_samples`, `devices`, `refresh_tokens`.
- Бэкап: ежедневный cron `sqlite3 panel.db ".backup …"` (или Go-эквивалент), хранение 7 копий. Восстановление = копия файла.
- Миграции: версионирование схемы (инструмент — на усмотрение билдера).

### 6.9 API (эскиз)
`/api/auth/login|refresh|logout|2fa/enroll|2fa/verify|2fa/disable` · `/api/users` CRUD · `/api/inbounds` CRUD · `/api/config` (GET/PUT raw routing + просмотр итогового конфига) · `/api/xray/status|start|stop|restart` · `/api/stats/*` · `/api/templates` CRUD · `/api/settings`. JWT-middleware на всё кроме `/api/auth/*` и `/sub/*`. HTTP-роутер: stdlib `net/http` (Go ≥1.22 patterns) — достаточно, фреймворк не нужен (мой выбор; билдер может обосновать иное).

## 7. Фронтенд

- **Svelte 5.59 (runes) + Vite 8.3.8 (Rolldown) + @sveltejs/vite-plugin-svelte 7.3.1 + Tailwind CSS 4.3.5 (@tailwindcss/vite) + shadcn-svelte 1.8.1** (версии проверены web-ресёрчем 20.11.2026, совместимы; shadcn-svelte ≥1.0 = только Svelte 5 + TW4; Node ≥20.19/22.12).
- SPA, сборка → `embed.FS` Go-бинарника. Тёмная тема в духе Remnawave. **Язык UI — русский** (мой выбор: админ один, русскоязычный).
- Страницы: Login (+2FA) · Dashboard · Users · Inbounds/Protocol · Routing (JSON-редактор) · Templates (подписки) · Settings (2FA, пароль, xray, интервалы) · Config viewer (итоговый xray.json).
- QR для TOTP — npm-либа на фронте (выбор за билдером). Графики — лёгкая либа (выбор за билдером, без тяжёлых дашборд-фреймворков).

## 8. Деплой и верификация (этап имплементации, не сейчас)

Реальные значения (IP, домены, порты, пути) подставляются из приватного runbook оператора на сервере — не из репо.

Целевой сервер — **выделенная VPS** (ADR-0008); старый сервер с Remnawave физически не затрагивается.

1. Сборка на машине оператора: Go cross-compile linux/amd64 + embedded SPA. Бинарник на сервер через SSH-инструментарий оператора.
2. Подготовка VPS (каждый шаг — явное «да»): swap 2 GB; проверить порты 80/443/8443/3002/10811; создать /opt/flypanel; скачать xray v26.11.9 (официальный релиз + checksum); systemd unit; `flypanel admin init`; UFW allow 22/80/443/8443.
3. DNS: оператор перенаправляет A-запись `<PANEL_DOMAIN>` на `<ENTRY_IP>`. Caddy: нативная установка → блок `<PANEL_DOMAIN>` → validate + reload → верификация :2019 + LE-сертификат.
4. **E2E нового канала**: xray-клиент на сервере через 8443 → `curl --socks5 … api.ipify.org` = **`<ENTRY_IP>`** (один IP; если задан `<EGRESS_IP>` — он). Подписки: все 4 формата отдают валидный контент. Онлайн-статистика: тестовый клиент виден в дашборде (IP + трафик).
5. Старый стек физически отдельно — регрессия на нём не требуется. Опционально: read-only проверка старого канала (отдельное явное «да»).
6. Откат: `systemctl stop flypanel`, закрыть 8443 в UFW, убрать Caddy-блок + reload, DNS вернуть при необходимости. Данные /opt/flypanel не трогаются.
7. Результат зафиксировать в приватном журнале оператора (вне репо).
